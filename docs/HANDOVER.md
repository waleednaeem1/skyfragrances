credential the owner must set, every placeholder shipped in the sample data, where each setting
lives, what is deliberately not in this version, what the motion layer is, and the evidence from
installing the ZIP the way the owner will.

## 1. Credentials the owner creates or sets

| Credential | Created where | Entered where | Stored where |
|---|---|---|---|
| Hostinger login | hostinger.com | hPanel only | — |
| MySQL database name, user, password | hPanel → Databases → Management | Installer screen 2 | `public_html/config.php` → `db` |
| `orders@skyfragrances.com` mailbox password | hPanel → Emails | Installer screen 2 (optional) | `config.php` → `smtp.pass` |
| Admin username + password (12+ chars) | Installer screen 3 | `/admin/login` | `admin_users.password_hash` (bcrypt) |
| Admin login on the live shop | Created by the developer at install | `/admin/login` | The developer tells the owner the username only; the owner sets his own password with `app/tools/reset-password.php` (guide Part 10). |
| Install key (32 hex) | Written by the installer to `storage/.install-key` | Installer screen 2, once | Deleted when the install finishes |
| `security.app_key` (64 hex), `security.cron_key` (32 hex) | Generated by the installer | Never typed | `config.php` → `security` |
| Maintenance preview key | Generated by the installer; regenerable | Typed on the closed page | `settings.maintenance_bypass` |
| Google Search Console verification | Google | Settings → SEO | `settings.google_verification` |

`config.php` is written once by the installer and set to mode `0400`. Nothing on the site ever
rewrites it. Changing the mailbox password means editing it by hand (guide, Part 10).

There is **no** password-reset email. Recovery is `app/tools/reset-password.php` (register C-64):
the owner copies it to `public_html/` in File Manager, opens it, creates the empty nonce file
`storage/reset-{16hex}` it names, and sets a new 12+ character password; the tool clears
`admin_login_attempts` for the account, deletes the nonce, its pending file and itself, and only
the browser that started the flow can finish it (cookie-bound, one hour). Guide Part 10 →
"Forgotten admin password" carries the steps; the phpMyAdmin hash paste stays there as the
fallback. Exercised over HTTP on 2026-09-29 (§8b).

## 5. Known limitations and deliberate decisions

1. **Password recovery is a File-Manager tool, not an email.** `app/tools/reset-password.php`
   (C-64) ships in the denied `app/` tree and must be copied to the root to run; it proves
   File-Manager access with a nonce file before showing the form and removes itself afterwards.
   The Tools page and the login page point at the guide's "Forgotten admin password" section.
2. **Home page product rows need ≥ 4 live perfumes.** `app/controllers/home.php` hides best
   sellers / new arrivals / for-whom rows when fewer than four active products exist and shows
   an "empty" hero instead. `/shop` lists everything regardless. The guide tells the owner to add
   perfumes before removing the samples.
3. **`install.php` self-deletes only on a production host.** On a local/dev address the
   installer keeps the file and shows the red "Delete install.php now" panel with a delete
   button. On skyfragrances.com it deletes itself (green panel).
4. **`sitemap.xml` returns 404 while `site_indexable = 0`.** The installer sets it to 0 on any
   host other than skyfragrances.com. On the real domain it is 1 from the start.
5. **Emails without SMTP.** If no mailbox is entered, emails are written to
   `storage/logs/mail-preview/` and queued in `email_outbox` with nothing sending them. Adding
   SMTP later is a `config.php` edit (guide, Part 10).
6. **No cron by default.** Order emails go out when an admin page is loaded (≤ 2 per load). A
   15-minute cron on `cron.php` is optional and needs the `cron_key` from `config.php` when
   called over HTTP; from the CLI it needs no key.
7. **Admin sessions are bound to the browser (user-agent).** A different browser = log in
   again. There is one admin account; no roles.
8. **Lock-outs:** 5 wrong passwords per username add a delay; 10 per IP return 429 for 15
   minutes. Cleared by time or by emptying `admin_login_attempts`.
9. **HSTS is off** (Q-23). One `.htaccess` line for a developer to add once the certificate has
   been stable for a while.
10. **Sub-folder installs are not supported** (C-71). The installer refuses unless the files are
    at the domain root.
11. **hPanel "Force HTTPS" must stay off on a fresh install** — the site does the redirect
    itself; Hostinger's switch prepends a competing rule. The live site runs with it (and the CDN)
    on and works; the guide tells the owner not to touch either there, and the decision is open
    (§9 item 13).
12. **Two kinds of update.** The full `skyfragrances-public_html-folder.zip` re-ships
    `install.php`, `.htaccess`, `robots.txt` and the sample images (guide Part 8b carries
    `config.php`, `storage/` and `uploads/` across; `install.php` must be deleted again; sample
    image files re-appear under `uploads/products/sample/` as harmless orphans if the sample rows
    were removed). The code-only update pack from `dev-tools/build-update-pack.sh`
    (`skyfragrances-update-YYYYMMDD-HHMM.zip`) leaves out `install.php`, `config*.php`, `dev/`,
    `storage/` and `uploads/` entirely; it still re-ships `.htaccess` and `robots.txt`, so after
    either kind the owner re-presses "Make HTTPS permanent" (the shipped `.htaccess` has the 302
    line) — guide Part 11 step 5.
13. **`.user.ini` sets `session.cookie_secure = 1`** — correct on the live https domain; on a
    plain-http local copy served by Apache/LiteSpeed the admin login would not stick. The
    PHP built-in server ignores `.user.ini`, so local testing with `php -S` is unaffected.
14. **Orders are never hard-deleted** from the panel; cancellation is the terminal state.
15. **Reviews** are customer-submitted and admin-approved only; the 8 seeded ones are unapproved
    and are removed with the sample data.
16. **Payment proofs** are re-encoded to JPEG and stored under `storage/proofs/YYYY/MM/`, served
    only through the admin (`/admin/orders/{n}/proof`).

## 6. The motion layer (formerly the `motion-wip` branch)

The scroll-driven motion layer is **part of the launch build** — finished on `motion-wip` and
merged into `main` in `0ff6deb` ("Merge the signature motion layer into the launch build"). It
ships in the ZIP and the deploy workflow refuses to finish unless the live home page serves it:

- `assets/js/motion/` — `config.js` (flags and the kill switches), `gate.js`, `core.js`
  (`type="module"`), section modules `hero.js`, `ribbons-gl.js`, `cards.js`, `story.js`,
  `micro.js`, `quiz.js`, `transitions.js`;
- `assets/js/vendor/` — GSAP + ScrollTrigger and Lenis, vendored with their licences
  (`LICENSE-gsap.txt`, `LICENSE-lenis.txt`); no CDN, no build step;
- `assets/css/motion.css`, assembled from `assets/css/motion/*.css` (`cat motion/*.css >
  motion.css`; the parts ship too), loaded on home, listing, collections, product and quiz;
- `assets/js/intro.js` + `app/partials/intro.php` (the monogram intro), `app/partials/transition-overlay.php`
  and the `sf-*` hooks in the views.

Every one of those paths is in `required_files` of `site/dev/zip-manifest.php`, so a build cannot
leave the layer out. It degrades on its own: mobile never loads GSAP, Lenis or the WebGL ribbons
(plates instead), `prefers-reduced-motion` loads no section module, and every buy-path element is
painted and hit-testable within 10 ms of `load` (`docs/motion/run-report.md`, harness
`dev-tools/motion-check.mjs`). If a real-device budget is missed, the kill-switch order is
`docs/motion/PLAN.md` §6.4 — flags in `config.js`, no code removal. Measured with the layer on:
`docs/lighthouse/summary.md` (98 / 98 / 96–98 mobile on the production-equivalent server) and
§7b below (the ZIP as installed). The owner needs to do nothing for it; the guide mentions the
intro only where the owner first opens the shop on a phone.

## Deploy over SSH (how code reaches the live site)

- Every push to `main` that touches `site/` runs `.github/workflows/deploy.yml`: PHP syntax check,
  then `rsync` over SSH into `~/domains/skyfragrances.com/public_html` on the Hostinger server
  (178.16.136.115, port 65002, user `u561152958`), then a live check that the home page serves
  the motion layer. It never touches `config.php`, `install.php`, `storage/` or `uploads/`.
  It does re-upload `.htaccess`, whose redirect line ships as `R=302`, so every deploy puts the
  HTTPS redirect back to temporary (§9 item 14). The owner is told (guide Part 11) that updates
  normally arrive by themselves within a minute and the ZIP methods are only for when the
  developer asks.
- Credentials: an ed25519 deploy key. Public half is registered in hPanel → Advanced → SSH Access →
  SSH keys (`skyfragrances-deploy`); private half lives only in the GitHub secret
  `SSH_PRIVATE_KEY` (plus `SSH_HOST`, `SSH_PORT`, `SSH_USER`; optional `SSH_REMOTE_DIR`).
  The developer's copy is `~/.ssh/skyfragrances_deploy` on the build Mac.
- To rotate: generate a new key, replace the secret, add the new public key in hPanel, delete the
  old one there. To disable deploys: delete the key in hPanel.
- The old FTP secrets (`FTP_*`) are unused and can be deleted.
- Manual fallback: `dist/skyfragrances-public_html-folder.zip` (full site, folder-wrapped) with the
  three-item preservation steps in GO-LIVE-GUIDE Part 8b, or the flat update pack from
  `dev-tools/build-update-pack.sh` extracted inside `public_html`.
